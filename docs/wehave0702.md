# 7iTAX 현재 문제 진단 및 개선 계획

작성일: 2026-07-03

## 1. 현재 코드 상태 요약

현재 프로젝트는 단순 아이디어 단계가 아니라 백엔드, 안드로이드 앱, AI 서버, DB, 배포 문서, 모니터링 구성이 모두 존재하는 상태다.

- Backend: Spring Boot 기반 API 서버
- Frontend: Android Kotlin/Jetpack Compose 앱
- AI: FastAPI 기반 챗봇/RAG/거래 분류 서버
- DB: PostgreSQL, Redis, ChromaDB
- Infra: Docker Compose, Jenkinsfile, Prometheus, Grafana, Alertmanager
- 문서: README, 포팅 매뉴얼, 모니터링 문서, 작업 로그 일부 존재

다만 현재 상태는 “기능 구현 흔적은 많지만, 운영 가능한 완성도와 포트폴리오 설득력은 아직 부족한 상태”로 보는 것이 맞다.

## 2. 기존에 생각한 문제점 검증

### 1. 이체 기능이 없다

판단: 틀림

이체 기능은 이미 존재한다.

- `POST /api/transfers/p2p`
- `POST /api/transfers/withdraw`
- `TransferController`
- `TransferService`
- `SsafyFinanceClient.transfer()`

다만 외부 금융망 연동이 아니라 DB 원장 기반 로컬 뱅킹 시뮬레이션으로 동작한다. 따라서 “이체 기능이 없다”가 아니라 “이체 기능은 있으나 로컬 원장 기반이며, SSAFY 네이밍 잔재와 운영 검증이 필요하다”라고 정리하는 것이 맞다.

### 2. 코드에 자신이 없다

판단: 맞음

백엔드 테스트 실행 결과:

```text
300 tests completed, 3 failed, 1 skipped
```

실패한 테스트는 장부 금액 관련 테스트 3개다.

- expected: 3,000,000 / actual: 3,300,000
- expected: 1,000,000 / actual: 1,100,000
- expected: 50,000 / actual: 55,000

모두 기대값보다 실제값이 10% 크다. 공급가액과 부가세 포함 금액 기준이 섞였을 가능성이 높다. 세금/장부 도메인에서는 치명적인 오류가 될 수 있으므로 우선 해결해야 한다.

### 3. AI 기능이 정상적으로 연동이 안 된다

판단: 부분적으로 맞음

AI 연동 코드는 존재한다.

- BE `AiServiceClient`
- BE `MockAiServiceClient`
- AI FastAPI 서버
- RAG, ChromaDB, Claude API 사용 구조

하지만 실제 동작에는 다음 조건이 필요하다.

- `ANTHROPIC_API_KEY`
- AI 서버 실행
- 임베딩 모델 다운로드
- ChromaDB 초기화
- BE의 `AI_SERVICE_BASE_URL` 설정
- Android 앱과 BE API 연결 확인

따라서 “AI 기능이 없다”가 아니라 “AI 연동 구조는 있으나 실제 운영 가능 상태, 키 설정, 모델 초기화, 성능 검증이 필요하다”가 정확하다.

### 4. 금융 연동망을 이용했기 때문에 해체해야 한다

판단: 절반은 이미 해체됨

README와 코드 기준으로 현재 핵심 금융 기능은 외부 금융망이 아니라 로컬 DB 원장 기반이다.

그러나 코드에 다음 잔재가 많이 남아 있다.

- `SsafyFinanceClient`
- `SsafyCreditCardClient`
- `Ssafy*Response`
- `ssafyUserKey`
- 문서 내 SSAFY 서버 주소
- Android release URL: `https://j14c203.p.ssafy.io`

따라서 할 일은 “금융망 해체”보다 “SSAFY 외부 의존성 잔재 제거, 네이밍 정리, 문서 정합성 확보”다.

### 5. 세금 데이터 분석이나 AI 핵심 기술 고도화 필요

판단: 맞음

세금 계산, 장부, VAT, 종합소득세, AI 분류 기능은 구현되어 있지만 검증과 수치화가 부족하다.

특히 현재 테스트 실패가 장부 금액 기준에서 발생했기 때문에 세금 계산 신뢰도를 먼저 회복해야 한다.

추가로 AI 쪽은 다음 고도화가 필요하다.

- 분류 정확도 측정
- RAG 응답 품질 평가
- 세법 문서 근거 표시
- 잘못된 세무 답변 방지
- Mock 모드와 실제 AI 모드 분리 문서화

### 6. 배포를 통해 안정성을 테스트해야 한다

판단: 맞음

Docker Compose, Jenkinsfile, 포팅 매뉴얼은 존재한다. 하지만 테스트가 실패 중이므로 배포 전에 최소한 다음이 필요하다.

- 백엔드 테스트 통과
- 로컬 Docker Compose 기동 확인
- BE, AI, DB, Redis 연결 확인
- Android 앱에서 로컬 API 호출 확인
- 주요 API smoke test
- 모니터링 대시보드 데이터 수집 확인

### 7. 금융 프로젝트 고도화를 위한 다양한 문제점 존재, S3 DB 저장

판단: 표현 수정 필요

현재 코드에서 AWS S3 저장 구현은 확인되지 않았다. 현재 저장 구조는 PostgreSQL, Redis, ChromaDB volume 중심이다.

따라서 “S3 DB 저장”이 아니라 다음처럼 정리하는 것이 맞다.

- 리포트 PDF/Excel 파일 저장소를 S3 또는 Object Storage로 분리할지 검토
- DB에는 파일 메타데이터만 저장
- 실제 파일은 S3 같은 외부 스토리지에 저장
- 개인정보/세무자료 암호화 및 접근 제어 필요

### 8. 멘토링 받았던 모든 내용 작성 필요

판단: 맞음

현재 코드 변경 로그는 일부 존재하지만, 멘토링에서 어떤 지적을 받았고 어떻게 개선했는지 정리되어 있지 않다.

포트폴리오에는 다음 구조가 좋다.

- 지적받은 문제
- 원인
- 개선한 내용
- 개선 전/후 차이
- 남은 한계

### 9. 실제 포트폴리오 수치화 필요

판단: 맞음

현재 기능 목록은 있지만 수치가 부족하다. 금융/세금/AI 프로젝트는 수치가 있어야 설득력이 생긴다.

수치화할 항목:

- 테스트 수: 백엔드 300개 실행, 실패 3개
- 실패 해결 후 통과율
- AI 분류 정확도
- RAG 평가 점수
- 세금 계산 테스트 케이스 수
- API 평균 응답시간
- p95 응답시간
- 5xx 에러율
- Grafana 대시보드 지표 수
- 알림 규칙 수
- 장애 감지 시간
- Docker 컨테이너 구성 수

### 10. 포팅 매뉴얼 확인 및 서버 배포

판단: 맞음

`exec/포팅_매뉴얼.md`는 존재한다. 다만 일부 문서가 인코딩 깨짐처럼 보이므로 정리 필요하다.

해야 할 일:

- 포팅 매뉴얼 인코딩 정리
- 현재 코드와 문서 내용 불일치 제거
- 로컬 실행 절차 검증
- 배포 서버 환경변수 목록 정리
- 실제 배포 후 접속 URL, 포트, 계정, 테스트 절차 기록

### 11. IPS 대시보드, 관리자 페이지, 모니터링

판단: 부분적으로 맞음

모니터링은 이미 구현되어 있다.

- Prometheus
- Grafana
- Alertmanager
- Actuator `/actuator/prometheus`
- 알림 규칙

하지만 다음은 부족하다.

- 관리자 페이지
- IPS 또는 보안 탐지 대시보드
- 로그 중앙화
- 개인정보 마스킹
- 감사 로그 저장소
- 분산 추적

즉 “모니터링 없음”이 아니라 “기본 모니터링은 있으나 금융권 운영 관점의 보안/관리자/로그 체계가 부족하다”가 맞다.

### 12. 은행/KDN 등에서는 운영시스템, 대규모 트래픽 트러블슈팅 경험이 중요하고 코드는 덜 중요하다

판단: 방향은 맞지만 표현 수정 필요

금융권에서는 단순 기능 구현보다 운영 안정성, 장애 대응, 모니터링, 트래픽 처리, 보안이 매우 중요하다.

하지만 코드는 안 중요한 것이 아니다. 좋은 포트폴리오는 “코드를 잘 짰다”보다 “운영 문제를 코드와 인프라로 어떻게 해결했다”를 보여줘야 한다.

포트폴리오 방향:

- 장애가 발생할 수 있는 지점 정의
- 지표 수집
- 알림 설정
- 병목 원인 분석
- 개선 전/후 수치 비교
- 장애 대응 시나리오 문서화

## 3. 우선순위별 개선 계획

## P0. 반드시 먼저 고칠 것

### 1. 백엔드 테스트 실패 3개 해결

현재 가장 먼저 해야 할 일이다.

실패 원인 후보:

- 장부 금액을 공급가액으로 볼지 부가세 포함 금액으로 볼지 기준 불일치
- 테스트 기대값이 과거 기준이고 코드가 변경됨
- VAT 계산 로직이 장부 합계에 중복 반영됨

해야 할 일:

- 실패 테스트 위치 확인
- BookEntry 금액 필드 의미 정리
- `amount`, `supplyAmount`, `vatAmount`, `totalAmount` 기준 명확화
- 테스트 기대값 수정 또는 서비스 로직 수정
- 백엔드 테스트 300개 전부 통과 확인

### 2. 문서 인코딩 깨짐 정리

README, 포팅 매뉴얼 일부가 깨져 보인다. 포트폴리오 문서로 쓰려면 반드시 정리해야 한다.

해야 할 일:

- README 재작성
- 포팅 매뉴얼 재작성 또는 인코딩 복구
- 현재 코드 기준으로 기능 설명 업데이트
- SSAFY 서버 주소, OAuth, 금융망 관련 설명 정리

### 3. 외부 의존성/SSAFY 잔재 정리

기능상 로컬 뱅킹으로 바뀌었지만 이름과 문서에 SSAFY 흔적이 남아 있다.

해야 할 일:

- `SsafyFinanceClient` → `LocalBankingClient` 또는 `LedgerBankingClient`
- `SsafyCreditCardClient` → `LocalCardClient`
- `Ssafy*Response` DTO 이름 정리 검토
- `ssafyUserKey` → `localUserKey` 또는 `bankingUserKey`
- Android release URL 수정
- 문서에서 외부 금융망 사용처럼 보이는 표현 제거

## P2. 운영/금융권 포트폴리오 강화

### 7. 모니터링 실제 구동 및 캡처

이미 Prometheus/Grafana 구성이 있으므로 포트폴리오에서 강점으로 만들 수 있다.

해야 할 일:

- Prometheus target UP 확인
- Grafana 대시보드 캡처
- 5xx 에러율 알림 테스트
- p95 latency 알림 테스트
- DB connection pool pending 알림 테스트
- 장애 상황과 복구 과정을 문서화

### 8. 관리자 페이지 또는 운영 대시보드 추가

현재 일반 사용자 앱 중심이다. 금융 프로젝트 고도화를 위해 관리자/운영자 관점이 있으면 좋다.

후보 기능:

- 사용자 목록
- 거래/이체 내역 조회
- 실패 거래 조회
- AI 분류 실패 내역
- 알림 발송 이력
- 감사 로그 조회
- 시스템 상태 조회

### 9. 보안/감사 로그 강화

일부 감사 로그 AOP는 존재한다. 하지만 금융권 포트폴리오로는 더 명확하게 보여줘야 한다.

해야 할 일:

- 감사 로그 저장 테이블 추가 검토
- 로그인/송금/결제/개인정보 조회 이벤트 기록
- IP, userId, action, result, timestamp 저장
- 주민번호/계좌번호/토큰 로그 마스킹
- Actuator 공개 범위 제한

### 10. 파일 저장 구조 개선 검토

현재 PDF/Excel 다운로드 중심으로 보인다. 장기적으로는 S3/Object Storage 구조가 더 자연스럽다.

개선안:

- PDF/Excel 생성
- Object Storage 업로드
- DB에는 파일 URL, ownerId, fileType, createdAt 저장
- 다운로드 시 권한 확인 후 presigned URL 제공

## 4. 포트폴리오에 넣을 수 있는 핵심 스토리

### 스토리 1. 외부 금융망 의존 제거

교육 과정 종료 후 외부 서버와 금융망에 접근할 수 없는 문제가 있었다. 이를 해결하기 위해 외부 금융 API 호출 구조를 로컬 DB 원장 기반으로 대체했다.

강조 포인트:

- 외부 API 장애/종료 상황 대응
- 로컬 원장 기반 입금/출금/이체 구현
- 트랜잭션 처리
- 비관적 락으로 동시성 고려
- 실패 거래 기록

### 스토리 2. 세금 자동화 파이프라인

결제/이체 데이터가 장부로 자동 생성되고, 세목 분류와 세금 계산으로 이어지는 구조를 만들었다.

강조 포인트:

- 거래 발생
- 장부 자동 생성
- MCC/AI 기반 세목 분류
- 부가세/종합소득세 계산
- PDF/Excel 출력

### 스토리 3. AI 세무 챗봇/RAG

세법 문서를 기반으로 RAG 챗봇을 구성하고, 거래 분류에도 AI를 활용했다.

강조 포인트:

- 세법 PDF 문서 처리
- ChromaDB 벡터 저장
- 로컬 임베딩 모델 사용
- Claude API 연동
- Mock 모드 제공
- AI 장애 시 폴백 처리

### 스토리 4. 운영 관측성 구축

## 6. 2주 남은 상황에서의 Pay 앱 로그인/보안 필수 TODO

목표는 모든 금융권 기능을 다 넣는 것이 아니다. 2주 안에는 “금융 Pay 서비스답게 로그인과 민감 거래를 통제한다”는 핵심 메시지를 완성해야 한다.

최종 README 방향:

```text
Risk-Based Authentication과 민감 거래 재인증을 적용한 금융 Pay 서비스
```

### 6-1. 반드시 구현할 것

### 1. 현재 로그인 흐름 안정화

현재 흐름은 본인인증 Mock → PIN 설정 → PIN 로그인 → JWT 발급 구조다. 이 흐름은 유지하되, 실제 앱처럼 보이도록 부족한 부분을 보강한다.

- [ ] 앱 시작 시 access token 존재 여부만 보지 말고, 만료 시 refresh token으로 재발급 시도
- [ ] refresh token도 실패하면 로그인/본인인증 화면으로 이동
- [ ] 저장된 phoneNumber가 없으면 PIN 로그인으로 보내지 않기
- [ ] 로그인 실패 메시지와 PIN 미설정 메시지 정리
- [ ] SMS 코드 입력 화면은 “Mock 인증”임을 코드/문서에서 명확히 정리

### 2. Refresh Token Rotation

현재 refresh token 재발급은 있으나, 토큰 재사용 탐지와 token family 개념은 없다. 2주 안에는 완전한 OAuth 서버 수준이 아니라도 “재사용 탐지 가능한 구조”까지 만드는 것이 좋다.

- [ ] refresh token을 Redis 또는 DB에 원문이 아니라 hash로 저장
- [ ] refresh token 재발급 시 기존 refresh token 폐기
- [ ] 이미 폐기된 refresh token이 다시 들어오면 탈취 의심 이벤트로 기록
- [ ] 탈취 의심 시 해당 userId의 refresh token 삭제
- [ ] 감사 로그에 `REFRESH_TOKEN_REUSE_DETECTED` 기록

### 3. 민감 거래 재인증

금융 Pay 앱에서 가장 포트폴리오 설득력이 큰 부분이다. 모든 API에 붙일 필요는 없고, 송금/출금/계좌등록/카드등록 같은 민감 기능에만 PIN 재확인을 요구한다.

- [ ] `POST /api/auth/reauth-pin` 추가
- [ ] PIN 검증 성공 시 Redis에 3분짜리 `reauth:{userId}` 저장
- [ ] 송금 API 실행 전 `reauth:{userId}` 존재 확인
- [ ] 출금 API 실행 전 `reauth:{userId}` 존재 확인
- [ ] 카드/계좌 등록 API에도 적용할지 결정
- [ ] 재인증 실패/만료 케이스 테스트 작성

권장 정책:

```text
일반 조회: access token만 필요
송금/출금/결제취소/계좌등록: access token + 최근 PIN 재인증 필요
```

### 4. 로그인 실패 제한과 계정 보호 정리

### 5. 최소 Risk-Based Authentication

AI나 복잡한 모델은 2주 안에 무리다. 대신 rule-based risk score로 충분히 은행권 느낌을 낼 수 있다.

최소 위험 점수 요소:

- 새 기기: +40
- 최근 5분 PIN 실패 3회 이상: +30
- 평소와 다른 IP 대역: +20
- 고액 송금: +30
- 새 수취인: +20

처리 정책:

- 0~30: 정상
- 31~60: 감사 로그 + 로그인 알림 이벤트 기록
- 61~80: PIN 재인증 요구
- 81 이상: 거래 차단 + 관리자 확인 대상 기록

2주 구현 범위:

따라서 앞으로의 방향은 새 기능을 많이 추가하는 것보다, 기존 기능을 안정화하고 운영/금융권 관점으로 정리하는 것이다.
